# 排障：怎么看报错

> 前端页面上那些红字（比如「连接中断」）**只是症状，不是原因**。
> 真正的原因在**服务端**：数据库的 `jobs.error` 字段、Redis 的进度记录、以及日志文件。
> 本文按「前端看到什么 → 去哪儿找 → 怎么读」的顺序讲。

---

## 一、先跑体检脚本（最快）

我在仓库里放了个一键排障脚本：

```bash
cd /www/wwwroot/bsum          # 换成你的实际项目路径
.venv/bin/python deploy/doctor.py
```

它会依次输出 5 节：配置依赖 / 进程状态 / 最近任务 / Redis 进度 / 日志异常，
最后给出结论。**90% 的情况看完它就定位到了。**

只想看某一个任务：

```bash
.venv/bin/python deploy/doctor.py 42      # 42 换成那个 job_id
```

`job_id` 怎么来？提交任务时浏览器 F12 → Network → 找 `POST /api/video` 的响应，
里面 `job_id` 字段就是。或者直接看数据库里最新的几条。

## 二、三个报错来源（按可靠程度排序）

### 来源 1：数据库 `jobs` 表 —— 最终结论，最可靠

任务失败时，Worker 会把错误信息写进 `jobs.error`：

| 字段 | 含义 |
|---|---|
| `status` | `pending` / `running` / `done` / `error` |
| `stage` | 卡在哪个阶段 |
| `error` | **失败原因（就是你要找的）** |
| `progress` | 百分比 |

查最近 10 条任务：

```bash
.venv/bin/python - <<'EOF'
import asyncio
from sqlalchemy import desc, select
from app.db.models import Job
from app.db.session import session_scope

async def main():
    async with session_scope() as db:
        rows = (await db.execute(select(Job).order_by(desc(Job.id)).limit(10))).scalars()
        for j in rows:
            print(f"#{j.id} [{j.status}] stage={j.stage} progress={j.progress}")
            if j.error:
                print(f"   错误: {j.error}")

asyncio.run(main())
EOF
```

或者直接在宝塔的 phpMyAdmin / 数据库面板里执行：

```sql
SELECT id, status, stage, LEFT(error, 300) AS err, created_at
FROM jobs
WHERE status = 'error'
ORDER BY id DESC
LIMIT 10;
```

### 来源 2：Redis 实时进度 —— 能看到「卡在哪一步」

进度是高频写的，走 Redis 不进数据库。key 格式 `bsum:progress:{job_id}`：

```bash
redis-cli --scan --pattern 'bsum:progress:*' | head
redis-cli get 'bsum:progress:42' | python3 -m json.tool
```

输出长这样：

```json
{
  "stage": "error",
  "message": "未配置 DeepSeek API Key。请在「设置」中填写你自己的 Key…",
  "percent": 100,
  "ts": 1757808000.0
}
```

`stage=error` 时，`message` 就是给用户看的错误原因。

> 也可以直接看队列积压情况：
> ```bash
> redis-cli llen rq:queue:bsum          # 队列长度，一直 >0 说明 Worker 没在消费
> redis-cli zcard rq:queue:bsum:failed  # RQ 层面失败的任务数
> ```

### 来源 3：日志文件 —— 有完整堆栈

生产环境（`APP_ENV=production`）日志会同时写文件：

```
logs/app.log       # Web 主日志，10MB 轮转，保留 5 份
logs/worker.log    # Worker 输出（bt_start.sh 重定向的）
logs/bootstrap.log # 初始化日志
```

看最近的错误：

```bash
tail -n 200 logs/worker.log | grep -A 30 -i 'traceback\|error'
tail -n 200 logs/app.log    | grep -i 'error\|exception'
```

**实时跟踪**（任务正在跑的时候用）：

```bash
tail -f logs/worker.log
```

> ⚠️ **区分两类错误：**
> - `logger.warning(...)` —— 可恢复的，代码里已经兜底了，不影响任务
> - `logger.exception(...)` —— 真出事了，**后面跟着 `Traceback` 才是关键**
>
> 尤其搜 `任务未预期失败` 和 `任务执行异常`，这两条后面接的堆栈就是根因。

## 三、前端那行红字对应的实体

前端 `subscribeJob()` 里 `error` 事件的处理（`app/static/common.js:149`）：

```javascript
es.addEventListener('error', (e) => {
  let msg = '连接中断';           // ← 兜底文案
  try { msg = JSON.parse(e.data).message || msg; } catch (_) {}
  handlers.onError && handlers.onError(msg);
  es.close();
});
```

**「连接中断」这个字面量只在两种情况下出现：**

1. 服务端 SSE 推送了 `event: error` 且 `data` 里**没有** `message` 字段
2. 解析 `e.data` 抛异常（比如事件是浏览器的网络错误，`e.data` 是 `undefined`）

服务端推 `error` 事件的地方在 `app/api/user/content.py:190`：

```python
if cur.status == JobStatus.ERROR:
    yield _sse("error", {"message": cur.error or "任务失败"})
```

正常情况下 `cur.error` 有值，前端会显示**具体原因**。
所以**如果只看到「连接中断」而没有具体消息，说明 `jobs.error` 是空的** ——
这通常意味着：

- Worker 进程被强杀（OOM / `kill -9`），还没来得及写错误就没了
- 数据库写入失败
- 任务还在 `running` 态但 SSE 连接因为 Nginx 超时被切断了

**这一条很重要**：查 `jobs.error` 如果为空，就去查 Worker 是不是被系统杀过：

```bash
dmesg -T | grep -i 'killed process'    # 看有没有 OOM 杀进程
journalctl -u bsum-worker -n 100       # 如果用 systemd 起的
tail -n 100 logs/worker.log            # 如果用 bt_start.sh 起的
2 核 4G 跑 yt-dlp + ffmpeg 是有可能被 OOM 的
```

## 四、按症状速查

| 前端表现 | 大概率原因 | 去哪查 |
|---|---|---|
| 一直「排队中」，进度条不动 | **Worker 没起来** | `pgrep -af app.workers.worker`；`logs/worker.log` |
| 一直「排队中」，但 Worker 在跑 | Redis 连不上 / 队列名不一致 | `.env` 的 `REDIS_URL`、`QUEUE_NAME`；`redis-cli llen` |
| 进度条卡在某一步不动 | Nginx 没关缓冲（经典坑） | 见 `宝塔部署.md` 的 SSE 配置 |
| 点「开始」立刻就红 | 提交接口本身报错 | F12 → Network → `POST /api/video` 响应体 |
| 「连接中断」无具体消息 | Worker 被杀 / DB 写失败 | `dmesg -T \| grep -i killed`；`jobs.error` 是否为空 |
| 「未配置 DeepSeek API Key」 | 后台没填 Key | 后台 → 密钥配置 |
| 「该视频没有字幕，且语音识别已被关闭」 | ASR 开关关了 | 后台 → 系统设置 → `enable_asr` |
| 「本月语音识别额度不足」 | 用量超了 | 后台 → 用量统计；`redis-cli get bsum:usage:{uid}:{YYYY-MM}` |
| 「音频时长 X 小时超过腾讯云单次上限」 | 视频太长 | 腾讯云 ASR 单次上限 5 小时，无解需分段 |
| 字幕提取失败但继续走 ASR | 正常兜底行为 | 无需处理，`logger.warning` 而已 |

## 五、几个常见根因的详细排查

### 1. Worker 没起来（最常见）

症状：提交任务后进度条一动不动，数据库里 `status` 一直是 `pending`。

```bash
# 有没有 Worker 进程
pgrep -af app.workers.worker

# 手动前台起一个，看它报什么错
.venv/bin/python -m app.workers.worker
```

常见原因：
- **Redis 连不上** —— 检查 `.env` 里 `REDIS_URL` 的端口和密码（宝塔装的 Redis 默认**有密码**）
- **数据库连不上** —— `DATABASE_URL` 里密码带特殊字符没转义
- **依赖没装全** —— `.venv/bin/pip install -r requirements.txt`

宝塔里如果是用 `bt_start.sh` 起的，Worker 会在 `.run/worker.pid` 里记 PID：

```bash
cat .run/worker.pid
ps -p $(cat .run/worker.pid)     # 还在不在
```

### 2. yt-dlp 解析失败

B 站现在**几乎必须带 Cookie**，否则解析不出音频地址。

```bash
# 手动验证 yt-dlp 能不能解析
.venv/bin/python - <<'EOF'
from app.services.downloader import YtDlpRunner
r = YtDlpRunner(cookie_file="", proxy="")
info = r.fetch_info("https://www.bilibili.com/video/BV1xx411c7mD")
print(info)
EOF
```

报 403 / 需要登录 → 去前台「个人设置」里粘贴 B 站 Cookie
（浏览器 F12 → Application → Cookies → 复制 `SESSDATA` 那一整行）。

### 3. ASR 相关

```bash
# 腾讯云密钥对不对
.venv/bin/python - <<'EOF'
import asyncio
from app.db.session import session_scope
from app.services.asr_service import get_asr

async def main():
    async with session_scope() as db:
        asr = await get_asr(db)
        print("engine:", asr.engine)

asyncio.run(main())
EOF
```

常见错误：
- `AuthFailure.SignatureFailure` → 密钥抄错了
- `FailedOperation.NoFreeAmount` → 免费额度用完了
- `ResourceUnavailable.AudioDurationExceed` → 超 5 小时

**注意 COS 和腾讯云 ASR 必须同地域**，否则会有外网流量费。
预签名 URL 只有几分钟有效期，服务器时间偏差过大会直接签名失败：

```bash
date                    # 服务器时间
timedatectl status      # 时区/同步状态
```

### 4. 前端进度条数值不动

这是**已知的小 bug**，不影响功能：服务端进度字段叫 `percent`，
而前端 `index.html:630` 读的是 `p.progress`（不存在），所以那个 `if` 永远不成立。
实际进度条是靠 `updateStep()` 按阶段跳的（5% → 25% → 60% → 85% → 100%），
所以看起来还是能走的。要修的话把那一行改成 `const pct = p.percent;` 即可。

## 六、把日志变详细

`.env` 里设：

```
APP_ENV=production     # 会写文件日志；设 development 只打控制台
LOG_LEVEL=DEBUG        # 如果支持的话，会打出 SQL 语句
```

改完记得**重启 Web 和 Worker**，否则不生效。

> 如果 `.env` 里没有 `LOG_LEVEL` 这个配置项（看 `app/core/config.py` 有没有），
> 那就只能靠 `APP_ENV` 控制 —— 非生产环境是 DEBUG 级别。

## 七、求助时该发什么

如果要问我或者问别人，把这三样发出来，基本一次就能定位：

1. `deploy/doctor.py` 的完整输出
2. `jobs` 表里那条失败记录的 `id` / `status` / `stage` / `error` 四个字段
3. `logs/worker.log` 里 `任务未预期失败` 或 `任务执行异常` **往后的 30 行**（含 Traceback）

**不要只发前端截图** —— 前端那个红框只是把服务端的错误消息显示出来，
如果服务端没记下原因，截图里就只有「连接中断」四个字，看不出任何东西。
